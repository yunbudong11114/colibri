# Colibri 模型工具名兼容设计

## 背景

Colibri 的内部工具名使用带命名空间的点号格式，例如 `files.read`、`memory.write`。这类名称便于注册、权限判断和日志阅读，但部分 OpenAI-compatible 服务只接受以下 function name 格式：

```text
[A-Za-z][A-Za-z0-9_-]*
```

百炼上的 Kimi 模型会因此在生成前返回 HTTP 400。当前会话层将该错误显示为“模型暂时不可用”，容易让人误判为模型 ID 或网络问题。

## 目标

- 保留 Colibri 内部清晰、稳定的点号工具名。
- Python 与 Rust 两个运行时提供一致的名称转换行为。
- 在 OpenAI-compatible 协议边界输出服务端可接受的 function name。
- 将模型返回的协议工具名无损还原为内部工具名。
- 同时转换当前工具声明和历史 assistant tool call，保证多轮工具会话合法。
- 映射对同一组工具确定且不存在名称冲突。

## 非目标

- 不重命名工具注册表、权限配置、转录日志中的内部工具名。
- 不为特定模型或供应商增加配置开关。
- 不改变会话层的模型错误展示策略。

## 设计

兼容逻辑属于 OpenAI-compatible 适配器，而不是工具注册表。Python 与 Rust 客户端各自在协议边界实现同一算法。每次 `complete` 根据本次工具声明及历史 assistant tool call 中出现的内部名称构建双向名称表：

1. 已符合协议格式的名称保持不变。
2. 非法字符连续段替换为 `_`。
3. 若名称不以字母开头，则增加 `tool_` 前缀。
4. 名称限制在 64 个字符内。
5. 若候选名称与本次请求中的其他名称冲突，则保留可读前缀并追加原始名称的短哈希。

发送请求时：

- 工具声明中的名称由内部名转换为协议名。
- 历史 assistant 消息中的 tool call 名称使用同一张表转换。

解析响应时：

- 已知协议名还原为内部名，再交给 `ToolRegistry`。
- 未知名称保持原样，由现有 unknown-tool 路径处理。

映射只存在于一次模型调用内，不进入持久化状态。会话历史、权限和转录仍只保存内部工具名。

两个运行时必须遵守同一组可移植约束、64 字符上限和冲突消解规则。任一运行时新增或调整映射规则时，都必须用对应测试同步验证另一实现，避免相同配置因入口不同而产生行为差异。

## 示例

```text
files.read       -> files_read
memory.write     -> memory_write
1wire.read       -> tool_1wire_read
```

若 `a.b` 与 `a_b` 同时存在，其中发生冲突的别名会追加稳定短哈希，避免错误地调用另一个工具。

## 测试

- 请求中的 dotted 工具声明会被转换。
- 历史 assistant tool call 使用相同协议名。
- 响应中的协议名会还原为内部名。
- 合法名称保持不变。
- 清洗后冲突的名称仍得到不同且可逆的协议名。
- 现有无工具、普通文本和图片请求行为不变。
- Python 与 Rust 测试使用相同的代表性输入和预期名称。
