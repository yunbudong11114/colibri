# CLI 微信扫码的小屏显示设计

## 目标与约束

在掌机自带 CLI App 中执行 `colibri auth weixin`，二维码必须完整可见、可以扫码；不使用 Mac 终端、不伪造登录流程、不展示真实登录凭据。截图使用隔离配置和明确标注的演示二维码。商店草稿不提交。

原实现固定 QR Version 5，使用双宽全块输出，带边距共 82 列、41 行。原生 CLI 为 45 列、10 行，输出会换行和滚动，无法完整扫码。

## 验证顺序

先在真实 CLI 验证紧凑点阵（Unicode Braille，单字符承载 2×4 模块）的可读性，检查字体支持、四周留白、完整显示以及二维码解码。这个实验不修改启动器、不暂停启动器、不替换系统字体。测试图必须从 framebuffer 截取，不用合成终端图片代替。

若紧凑点阵不能可靠解码，不发布这种方案，也不以截图掩盖问题。届时需要启动器支持图形二维码，或使用独立扫码视图；两者应明确区分，不能把外置视图声称为原生 CLI 的图像能力。

## 候选实现边界

通用 Rust QR 编码/终端输出与设备展示分离；桌面终端保持正常二维码。小屏自动识别终端尺寸。只在真实渲染和扫码验证通过后启用小屏模式。超出可显示容量时明确提示，禁止截断二维码。认证状态轮询、超时与配置保存沿用原核心，不把二维码写入对话日志。

## 商店说明

详情注明安装包及安装后的存储占用主要来自离线语音识别模型。本次只编辑草稿，不提交发布。

## 真机实验结果

2026-11-25 在掌机原生 CLI（bash PTY）中输出隔离的非认证演示数据。Unicode Braille 字符在当前安装的终端字体中显示为缺字方框，不能构成可扫描二维码；因此紧凑点阵方案不通过，不进入生产代码。截图证据保存在本机临时 QA 目录，不能作为商店功能截图。原生 CLI 没有可供 Colibri 使用的图形二维码输出接口，需要启动器侧能力配合。没有替换系统字体、暂停启动器或安装不可靠的字符方案。

## 已授权实现方案

普通终端使用半块字符（每字符上下两个模块），二维码采用标准编码库自动选择最小可容纳版本，保留四模块静区，使用白底黑码，避免依赖终端主题。原始登录链接不再默认输出。

掌机由原有 CLI 认证流程调用同一个 `/usr/bin/colibri` 的私有扫码视图，不增加独立可执行文件、运行库、字体或静态二维码图片。Rust 只通过匿名管道发送二维码矩阵；临时认证内容不落盘。视图复用现有 LVGL 和字体，二维码按整数像素放大且保留静区。

原生 CLI 与独立扫码页共用 framebuffer，必须独占显示。只在进程祖先中发现同一用户的官方启动器时临时暂停其绘制进程。独立的短生命周期恢复守护进程持有原 framebuffer 和亮度快照：显示进程正常结束、崩溃或被终止，控制管道关闭后恢复画面和亮度并恢复启动器。恢复守护脱离终端进程组，避免 Ctrl+C 同时终止恢复逻辑。无法取得安全显示所有权时不启动图形视图，并明确提示。不会修改启动器文件、系统字体或用户设置。

扫码结束、超时、取消均关闭视图，回到原 CLI；Esc 取消等同 Ctrl+C，不保存部分认证。普通终端/重定向输出使用半块文本路径。测试使用隔离目录和明确标注的演示二维码，检查真实截图可解码、取消恢复、进程被杀后的恢复、配置未改变。

比较修改前后的最终 deb 体积。替换自写固定版本编码器，避免重复编码实现；新增标准编码库只静态链接，无新增设备运行依赖。


## 实现与验证记录

- 自动版本编码使用固定上游 v1.8.0 的 Nayuki Rust 实现（MIT、无运行时依赖），移除原固定 Version 5 编码器。网络镜像缺少 crate 索引，故以保留原许可证的 vendored 方式固定源码；构建不需要访问该镜像。
- 普通终端使用四模块静区和白底黑码；真实 CLI 输出恢复为像素后，12/92/244 字节的三个演示 payload 均可解码，分别为 29×15、45×23、65×33 字符。当前典型登录长度从 82×41 降至 45×23。
- 掌机从系统自带 CLI 的 bash 启动隔离配置认证流程；实际 framebuffer 截图为完整 135×135px 二维码，独立解码器验证通过。截图明确标注演示码，不能用于登录。
- 手动取消、模拟认证成功、SIGKILL 扫码页、SIGKILL 认证进程，均验证启动器恢复，取消/强制终止不保存认证。
- 扫码页独占键盘后再恢复，避免退出扫码页时把 Esc 传给原 CLI。
- Rust 全套测试通过，认证输出即时刷新、凭据不打印等测试继续通过。真实微信账号登录由用户测试，QA 不使用真实账号或登录凭据。
